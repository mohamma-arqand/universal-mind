# معماریِ عمیق — ابرپلتفرمِ جذب‌کننده (نسخهٔ فنی، ویژهٔ ویندوز)

> این سند، «نقشه» را موشکافانه باز می‌کند: هر فاز، مکانیزم واقعیِ اتصال، و
> آنچه از نظر فنی روی Windows 11 ممکن است. برای مهندسِ داخلِ پروژه نوشته شده،
> نه برای نمایش.

---

## بخش ۱ — سنگِ بنای فنی: سه مکانیزمِ اتصال به «هر چیزی»

هیچ ابزاری را نمی‌شود «به‌صورت سحرآمیز» جذب کرد. روی ویندوز، **هر نوع ابزار فقط
از یکی از این سه راه** به پلتفرم وصل می‌شود. این سه برش، پوستِ فنیِ کل نقشه است
و همهٔ فازها روی آن می‌نشینند.

### مکانیزم ۱ — اتصالِ فرمانی (subprocess)

**چیست:** پلتفرم، یک برنامهٔ بیرونی را مثل یک «کارمند» از خط فرمان صدا می‌زند،
ورودی می‌دهد و خروجی می‌گیرد.

**برای چه ابزارهایی:** هر برنامه‌ای که CLI دارد (python، node، ffmpeg، git،
مبدل‌های فایل، ابزارهای فرمان‌خطی، و هر ایجنتِ کدنویسی که از ترمینال صدا زده می‌شود).

**مثالی ملموس:** به‌جای اینکه تو دستی ffmpeg را باز کنی و بگویی «این ویدیو را
فشرده کن»، پلتفرم فرمان `ffmpeg -i in.mp4 out.mp4` را اجرا می‌کند و خروجی را می‌گیرد.

**وضعیت در پروژهٔ فعلی:** ✅ **مکانیزم موجود است** — کلاس `ShellSpecialist` در
`io/adapters.py` (خط 251 به‌بعد) دقیقاً همین را می‌کند: فرمان را در یک جعبهٔ شنیِ
موقت اجرا می‌کند و خروجی را برمی‌گرداند. فقط باید «لیست سفید» (whitelist)ش
گسترده شود تا ابزارهای واقعی بیشتری را بپذیرد.

### مکانیزم ۲ — اتصالِ سرویسی (API / HTTP)

**چیست:** پلتفرم با یک سرویسِ آنلاین یا محلی از طریق یک قراردادِ وب (HTTP/JSON)
حرف می‌زند.

**برای چه ابزارهایی:** هر سرویسِ API (جیمیل، اسلک، هوش مصنوعی‌ها، سرویس‌های ابری)،
و هر برنامه‌ای که یک سرور محلی باز می‌کند (مثل برخی اپ‌های دسکتاپ).

**مثالی ملموس:** پلتفرم به‌جای اینکه تو وارد جیمیل شوی، به APIِ جیمیل `POST` می‌زند
و ایمیل را می‌فرستد.

**وضعیت در پروژهٔ فعلی:** ✅ **مکانیزم موجود و بالغ** — `HttpChatProvider` و
`Gateway` در `io/gateway.py`. این بخش از قبل تست‌شده و ضدفلکه است (من در دور پنجم
race شبکهٔ ویندوزش را رفع کردم).

### مکانیزم ۳ — اتصالِ اشیائی (COM / object model)

**چیست:** پلتفرم، یک نرم‌افزارِ نصب‌شدهٔ ویندوز را از طریق «مدل شیء» آن برنامه
(COM Automation) کنترل می‌کند — یعنی نه از طریق کدِ داخلی آن، بلکه از طریق
دستگیره‌ای که خودِ برنامه برای خودکارسازی عرضه می‌کند.

**برای چه ابزارهایی:** برنامه‌های آفیس (اکسل، ورد، پاورپوینت)، و هر برنامه‌ای که
COM server دارد. این تنها راهِ «بازِ» کنترلِ نرم‌افزارهای بسته است.

**مثالی ملموس:** به‌جای اینکه تو اکسل را باز کنی و سلول‌ها را دستی پر کنی، پلتفرم
از طریق COM به اکسل می‌گوید «سلول A1 را ۱۰ کن، بعد فایل را ذخیره کن».

**وضعیت در پروژهٔ فعلی:** 🚧 **هنوز ساخته نشده** — ولی فنیاً ممکن است، چون PowerShell
در دسترس است و `New-Object -ComObject Excel.Application` را پشتیبانی می‌کند (تأیید شد:
PowerShell و cmdletهای لازم روی این سیستم موجودند).

### جدولِ خلاصهٔ سه مکانیزم

| مکانیزم | راهِ اتصال | برای چه | وضعیت فعلی |
|---|---|---|---|
| ۱. فرمانی (subprocess) | CLI / ترمینال | برنامه‌های خط فرمان، ایجنت‌ها | ✅ موجود (`ShellSpecialist`) |
| ۲. سرویسی (API) | HTTP/JSON | سرویس‌های آنلاین، اپ‌های سرورمحور | ✅ موجود (`HttpChatProvider`/`Gateway`) |
| ۳. اشیائی (COM) | Object Model ویندوز | آفیس و برنامه‌های COM | 🚧 باید ساخته شود |

## بخش ۲ — «جذب» در برابر «اتصال»: مرزِ واقعی و دقیق

| اندازه‌گیری | اتصال (connect) | جذب (absorb/rewrite) |
|---|---|---|
| معنای فنی | دریافتِ نتیجه از ابزار و فراموش کردنِ جزئیات | خواندنِ قابلیت و ساختِ یک پیاده‌سازیِ داخلیِ مستقل |
| برای ابزارِ بسته (کد قفل) | ✅ ممکن | ❌ غیرممکن (کد در دسترس نیست) |
| برای ابزارِ باز (کد در دسترس) | ✅ ممکن | ✅ ممکن |
| برای API (قراردادِ روشن) | ✅ ممکن | ✅ ممکن (اگر اسپکِ API باز است، نسخهٔ داخلی ساخت) |
| خروجی | «از ابزار استفاده کردم» | «دیگر به ابزار نیاز ندارم، خودم دارمش» |

**نتیجهٔ مهندسی:** «جذب» = «اتصال» + «مطالعهٔ قابلیت» + «بازسازی». یعنی زیربنای
جذب، همان اتصال است. به همین دلیل، معماری اول «اتصالِ کامل» را می‌سازد، بعد
«لایهٔ جذب» را روی آن می‌نشاند. این ترتیب، از نظر فنی تنها ترتیبِ ممکن است.

## بخش ۳ — تشریحِ عمیقِ هر فاز (رفتن از «ما داریم» به «ما ساختیم»)

### فاز A — دانشنامهٔ ابزار (Tool Registry)

**هدف:** یک ساختار دادهٔ واحد که برای هر ابزار ثبت می‌کند: «چه توانایی دارد»،
«با کدام مکانیزم (۱/۲/۳) وصل می‌شود»، «باز است یا بسته (قابل جذب یا نه)»، و
«چقدر قابل‌اعتماد است».

**رابطِ پیشنهادی (اسکلت واقعی):**

```
ToolEntry
├── capability      : چه توانایی‌ای (مثل "edit_image") — نه اسم ابزار
├── connection      : مکانیزم (subprocess | http | com)
├── call_spec       : چطور صدا زده می‌شود (command / url / progid)
├── absorbable      : bool — آیا کدش در دسترس است و می‌شود بازنویسی کرد
├── contract        : هزینه، سرعت، برگشت‌پذیری، دادهٔ لازم
└── evidence        : رکوردِ عملکرد گذشته (برای داوری و رقابت)
```

**منطق:** مغز به‌جای حفظِ اسم ابزارها، فقط «توانایی» را می‌داند و در دانشنامه
دنبالِ «بهترین ابزارِ دارای این توانایی» می‌گردد. این یعنی یک ابزار قابل تعویض
است بدون اینکه مغز عوض شود.

**معیار تمام‌شدن فاز A:** حداقل یک ابزار از هر سه مکانیزم (فرمانی، API، COM) در
دانشنامه ثبت شود و واقعاً صدا زده شود و خروجی برگرداند.

### فاز B — اتصالِ گسترده (Universal Connectors)

**هدف:** پیاده‌سازیِ یک «اتصال‌دهنده» برای هر سه مکانیزم، به‌صورتی که هر ابزارِ
جدید فقط با یک «برچسب» وارد شود و بقیهٔ کارها خودکار باشد.

**سه اتصال‌دهندهٔ لازم:**
- `SubprocessConnector` — هر CLI را صدا می‌زند (بسطِ `ShellSpecialist`).
- `HttpConnector` — هر API را صدا می‌زند (بسطِ `Gateway`).
- `ComConnector` — هر برنامهٔ COM را کنترل می‌کند (جدید، از طریق PowerShell).

**معیار تمام‌شدن فاز B:** ۳–۵ ابزارِ واقعیِ متفاوت (یک CLI، یک API، یک برنامهٔ COM
مثل اکسل) متصل باشند و در یک درخواست واحد هماهنگ شوند.

### فاز C — جذب و بازنویسی (Absorption)

**هدف:** برای ابزارهای «باز»، قابلیت را مطالعه کن و یک پیاده‌سازیِ داخلی بساز که
دیگر به ابزار اصلی وابسته نیست.

**مکانیزم:** این دقیقاً جایی است که «Power Zero» (که پروژه از قبل دارد —
`powers/generator.py`) وارد می‌شود: یک توانایی را به کدِ قابل‌اجرا تبدیل می‌کند،
در جعبهٔ شنی می‌سازد، محک می‌زند، و فقط اگر بهتر از نسخهٔ اصلی بود، می‌پذیرد.

**محدودیت صادقانه:** فقط برای ابزارهای باز ممکن است (API با اسپک روشن، ابزار
متن‌باز، ایجنت‌ها). ابزارهای بسته (فتوشاپ) هرگز جذب نمی‌شوند — همیشه از طریق
«اتصالِ COM/API» استفاده می‌شوند.

**معیار تمام‌شدن فاز C:** یک ابزارِ بازِ واقعی، جذب شود و نسخهٔ داخلی‌اش بدون
ابزار اصلی کار کند و بهتر جواب بدهد.

### فاز D — ترکیبِ هوشمند (Orchestrated Synthesis)

**هدف:** مغز، چند ابزار را برای یک درخواستِ واحد هماهنگ کند، خروجی‌ها را یک
«D» کند که هیچ ابزارِ تکی تولیدش نکرده.

**منطق:** این بخش از قبل در پروژه هست (`synthesis.py` + `compose.py` —
«سنتز، نه یکپارچه‌سازیِ ساده»). فاز D آن را از «دو متخصصِ از پیش تعیین‌شده» به
«هر ترکیبی از ابزارهای دانشنامه» تعمیم می‌دهد.

**معیار تمام‌شدن فاز D:** یک درخواستِ واقعی که سه ابزارِ مختلف را به کار گیرد،
یک خروجیِ واحد بدهد که هیچ‌کدام به‌تنهایی نمی‌توانست بسازد.

### فاز E — خودتکاملی روی ابزارها (Merit Learning)

**هدف:** پلتفرم بعد از هر استفاده، یاد بگیرد کدام ابزار برای کدام توانایی بهتر
بود، و به‌مرور جایگزینِ بهتری بسازد.

**منطق:** PROMETHEUS (که از قبل هست) همین کار را برای «داوری» می‌کند؛ فاز E آن را
به «انتخاب و ترکیبِ ابزارها» تعمیم می‌دهد — نه فقط داوری، بلکه انتخابِ ابزارِ
بهتر بر اساس شواهدِ عملکرد.

**معیار تمام‌شدن فاز E:** بعد از چند بار استفاده، پلتفرم برای یک توانایی، ابزارِ
بهتر از حالت اولیه را انتخاب کند (با شواهد).

## بخش ۴ — ترتیبِ ساخت (چرا این ترتیب؟)

```
A (دانشنامه) → B (اتصال) → C (جذب) → D (ترکیب) → E (خودتکاملی)
```

**چرا این ترتیب؟** هر فاز، فازِ بعد را ممکن می‌کند:
- بدون A، مغز نمی‌داند چه دارد (نمی‌تواند B بسازد).
- بدون B، اتصالی وجود ندارد (نمی‌توان C جذب کرد).
- بدون C، بازنویسی‌ای نیست (D فقط «اتصال» را ترکیب می‌کند، نه «توانایی» را).
- بدون D، «بیشتر از مجموع» محقق نمی‌شود.
- E دائمی‌ترین مزیت است — یادگیریِ بلندمدت.

## بخش ۵ — خلاصهٔ شکاف «داریم → می‌خواهیم»

| جزء | داریم؟ | فازِ لازم |
|---|---|---|
| اتصال فرمانی | ✅ | — (بسط در B) |
| اتصال API | ✅ | — (بسط در B) |
| اتصال COM | 🚧 | B |
| دانشنامهٔ یکپارچهٔ ابزار | ⚠️ ناقص | A |
| جذب/بازنویسی | 🚧 | C |
| ترکیبِ چندابزار | ⚠️ (برای ۲ متخصص، نه N ابزار) | D |
| خودتکاملی روی ابزارها | ⚠️ (برای داوری، نه ابزار) | E |

---

**نتیجه:** معماریِ عمیق، یک چیز را قطعی می‌کند: **«جذب» و «اتصال» دو فرایندِ
جدا نیستند؛ جذب، اتصالِ به‌علاوهٔ مطالعه و بازسازی است.** پس راهِ درست، ساختنِ
فاز A (دانشنامه) و B (سه اتصال‌دهنده) است که هم‌اکنون از نظر فنی در دسترس‌اند —
و سپس C/D/E را روی آن بنا می‌کنیم. هر فاز با یک معیارِ قابل‌سنجش تمام می‌شود،
نه با «حس می‌کنم تمام شد».
